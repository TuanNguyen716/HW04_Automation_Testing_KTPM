# Automation Test Builder

Input: a feature + its written test cases. Output: Playwright files that another
person can extend by editing a CSV, not by editing code.

**Never invent a selector, URL, credential, error message or behaviour.** If the
input does not state it, emit `TODO_<THING>` in the code and list it under
*Assumptions / Missing info* in the summary. A wrong guess that silently passes is
worse than a TODO.

## Usage

```text
"Automate FR-02 (login & account lock) from docs/Test-cases.md"   -> generates spec + csv
"Add the locked-account cases to FR-02"                           -> edits the csv only
"Set up Playwright for this project"                              -> config + fixtures only
```

The same Skill serves FR-01, FR-02, FR-03 ... unchanged: the feature id only decides the
file names and the CSV columns.

## Input contract

Ask for whatever is missing before generating (one round of questions, not many):

| Input | Needed for | If absent |
| --- | --- | --- |
| Feature / requirement id + description | file names, `describe` title | ask - cannot proceed |
| Test cases (steps + expected result) | the flow and the assertions | ask - cannot proceed |
| Test data requirements | CSV columns and rows | derive from the test cases, flag it |
| SUT info (base URL, routes, accounts) | `baseURL`, `page.goto()` | `TODO_BASE_URL` / `TODO_PATH` |
| Existing selectors / page structure | locators | use semantic guesses **marked** `TODO_LABEL` |

## Output layout

Generate into the Playwright project root (here: `src/`), reusing what exists:

```
src/
  playwright.config.ts      <- templates/playwright.config.ts   (once)
  tests/
    fixtures.ts             <- templates/fixtures.ts            (once, shared)
    fixtures.check.spec.ts  <- templates/fixtures.check.spec.ts (once, CSV parser unit check)
    fr-01-<feature>.spec.ts <- templates/feature.spec.ts        (per feature)
  data/
    fr-01-<feature>.csv     <- templates/feature.csv            (per feature)
  playwright-report/        <- generated by the HTML reporter
```

One spec + one CSV per feature. `fixtures.ts` and `playwright.config.ts` are written
once and reused by FR-01, FR-02, FR-03 ... - never fork them per feature.

## Workflow

1. **Analyse** the test cases: split each into *fixed flow* (same for every case) and
   *varying data* (inputs + expected results). If two test cases share a flow, they
   are two CSV rows, not two tests.
2. **Design the CSV** (`templates/feature.csv`): one row per test case. Always include
   `tc_id`, `title`, the inputs, and the expected outcome columns
   (`expect_success`, `expected_url_path`, `expected_message`, ...). Expected values
   belong in the CSV too - that is what makes the spec generic.
3. **Generate the spec** from `templates/feature.spec.ts`: read the CSV at module
   level, `for (const row of rows) test(...)`. No inline arrays/objects of test data.
4. **Assertions** - at least 3 *distinct* patterns per feature, each one meaningful
   for the step it follows:
   `toHaveURL` (navigation) · `toContainText`/`toHaveText` (messages, content) ·
   `toBeVisible`/`toBeHidden` (appearance) · `toHaveValue` (input state) ·
   `toBeEnabled`/`toBeDisabled` (control state).
   Assert what the test case's *Expected result* actually says; do not pad the count.
5. **Browsers** - `playwright.config.ts` already defines `chrome` (channel `chrome`),
   `edge` (channel `msedge`), `firefox`. Every spec runs on all three; do not add
   `test.skip` per browser unless a test case says the behaviour differs.
6. **HTML report** - the config passes `title: 'Run by: 20127420 - Nguyễn Trần Minh Tuấn'`
   to the `html` reporter (rendered as the report header + browser tab title), and
   `fixtures.ts` repeats it as a `Run by` annotation shown on every test's detail page.
   Both are config-driven: never edit the generated report by hand. Do not use
   `config.metadata` for this - Playwright 1.63's HTML report leaves custom metadata
   keys unrendered.
7. **Validate** before reporting done:
   ```bash
   cd src
   npx playwright test tests/fixtures.check.spec.ts   # CSV parser still sane
   npx playwright test --list                 # every row x 3 browsers appears
   BASE_URL=<url> npx playwright test         # only if the SUT is reachable
   npx playwright show-report                 # header must read "Run by: 20127420 - ..."
   ```
   `--list` works without a running SUT and proves the CSV loaded. The stamp lives in
   the report's compressed payload, so check it in the rendered report, not with grep.
8. **Summarise**: files written, datasets x browsers = test count, assertion patterns
   used, and a short *Assumptions / Missing info / Risks* list (every `TODO_` left in
   the code must appear there).

## Quality rules

- Locators: `getByRole` > `getByLabel` > `getByPlaceholder` > `getByTestId`. CSS/XPath
  only when the input explicitly gives one.
- No `waitForTimeout`. Web-first assertions and `expect(...).toPass()` already retry.
  A real wait is `await expect(locator).toBeVisible()` or `page.waitForURL()`.
- One flow per feature. Branch on the expected outcome (`isTrue(row.expect_success)`),
  never copy the flow into a second test.
- CSV values are strings: use `isTrue()` for booleans, `Number(row.x)` for numbers.
- Shared setup goes in `beforeEach`; shared helpers go in `fixtures.ts`.
- Keep `tc_id` in the test title so report rows map back to the test-case document.

## Files

- `templates/playwright.config.ts` - 3 browsers + HTML reporter titled `Run by: ...`
- `templates/fixtures.ts` - CSV parser/reader, `isTrue`, `test` with the `Run by` annotation
- `templates/fixtures.check.spec.ts` - unit check for the CSV parser (no browser needed)
- `templates/feature.spec.ts` - data-driven spec skeleton with 5 assertion patterns
- `templates/feature.csv` - CSV header/rows skeleton
- `examples/login/` - runnable fictional login feature (spec + csv + 2-page demo app)

Zero extra npm dependencies: the CSV parser in `fixtures.ts` handles quotes, embedded
commas/newlines and BOM. Swap it for `csv-parse/sync` only if a dataset needs more.
